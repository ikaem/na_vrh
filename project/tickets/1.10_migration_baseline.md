# 1.10 Migration baseline

**Epic:** 1, Project foundations (see [epics.md](../epics.md))
**Spec refs:** sections 10 and 14 of [SPEC.md](../SPEC.md) (Data model: "Version the schema from day one, with migrations")
**Depends on:** 1.9 (all four tables exist)
**Status:** Todo

## Why
The spec asks for a versioned schema with migrations from day one. This ticket records the schema as it stands after the four tables (1.6 to 1.9) as version 1, and sets up Drift's migration tooling, so the first real schema change is a routine step instead of a scramble. There is no upgrade to write yet, because there is no version 2.

## Scope
- Configure Drift's migration tooling in `app/build.yaml`: a `databases:` entry mapping `app_database` to `lib/src/data/database/app_database.dart`, plus `schema_dir: drift_schemas/` and `test_dir: test/drift/` (the tool's defaults, written out so they are visible).
- Run `fvm dart run drift_dev make-migrations` once to record the version 1 schema. It writes `drift_schemas/app_database/drift_schema_v1.json`, which is committed.
- Add a "Changing the database schema" section to `app/README.md` with the workflow below.
- Do not add an `onUpgrade` step. Nothing can upgrade from a version that does not exist yet. The default creation of all tables on a fresh database stays, and so does the `beforeOpen` foreign-key step from 1.5.

## Workflow to document
After the first release, every schema change follows these steps:
1. Change the table definitions.
2. Increase `schemaVersion` in `AppDatabase`.
3. Run `fvm dart run drift_dev make-migrations`. It writes the new schema dump (`drift_schema_vN.json`), generates `app_database.steps.dart` (a step-by-step upgrade helper), generates test helpers under `test/drift/app_database/generated/` and a `migration_test.dart`, and prints an `onUpgrade: stepByStep(from1To2: ...)` snippet.
4. Paste the snippet into `AppDatabase.migration` and write the step.
5. Run the generated migration test.
6. Commit all of it, generated files included (decision from 1.4).

Before the first release, there is a shorter path (decision 2): delete `drift_schema_v1.json` and run the command again, without changing the version.

## Out of scope
- Writing any actual migration (there is no version 2).
- Data migrations.
- A CI check for the schema files (1.12).

## Acceptance criteria
- [ ] `app/build.yaml` has the `databases:` entry and the two directory settings.
- [ ] `drift_schemas/app_database/drift_schema_v1.json` is committed and lists the four tables: expeditions, routes, readings and photos.
- [ ] Running `fvm dart run drift_dev make-migrations` again leaves `git status` clean.
- [ ] Manual check, not committed: changing a table without bumping the version makes the command fail with an error instead of overwriting the dump.
- [ ] The README has the "Changing the database schema" section with the steps above.
- [ ] `fvm dart run build_runner build` leaves `git status` clean, and analyze, tests and the format check pass.

## Technical notes
- **Checked ahead of time** on a throwaway copy of the project, with a probe table:
  - With one schema version, the command writes only the schema dump. The step helper, the generated test helpers and the migration test appear once there is a second version. Simulating version 2 produced `drift_schema_v2.json`, `app_database.steps.dart`, `test/drift/app_database/generated/` (three files) and `migration_test.dart`, and printed the `stepByStep` snippet.
  - **Built-in guard:** when a table changes but the version does not, the command stops with "A schema for version 1 of the app_database database already exists and differs from the current schema. Either delete the existing schema file ... or update the schema version". So a schema change without a version bump, or a deleted dump, cannot slip through silently. CI (1.12) can run the command and fail on an error or a dirty tree.
  - The generated migration test checks every upgrade path from each recorded version to each later one, on an empty database, using Drift's schema verifier.
- At the first migration, the generated files (`app_database.steps.dart`, `test/drift/**/generated/`) may need adding to the analyzer excludes, next to `**/*.g.dart`. This ticket generates none of them, so check it then.
- The step helper and the migration test come from the Drift version in use (`drift_dev` 2.35.x at the time of writing). Check Drift's documentation if the command's output differs.

## Decisions
1. **The baseline is recorded after all four tables exist,** so version 1 is the complete initial schema.
2. **Before the first release, schema changes re-record version 1** (delete the old dump, run the command again) instead of writing migrations. There are no installed users yet whose data must survive. From the first release, or the first time data must be kept, every change is a new version with a step and its generated test.
3. **No `onUpgrade` until version 2.**
