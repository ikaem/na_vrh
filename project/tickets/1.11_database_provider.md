# 1.11 Database provider

**Epic:** 1, Project foundations (see [epics.md](../epics.md))
**Spec refs:** section 14 of [SPEC.md](../SPEC.md) (Tech stack: Drift, Riverpod)
**Depends on:** 1.4 and 1.5 (done), 1.10
**Status:** Todo

## Why
Every repository and feature will need the database. This ticket opens the real on-device database in one place and hands it to the app through Riverpod. It is also the first real `@riverpod` provider, so it sets the pattern, and the test helper for overriding providers, which ticket 1.4 left for the first real provider.

## Scope
- Add `lib/src/data/database/app_database_provider.dart` with two keep-alive providers (`@Riverpod(keepAlive: true)`):
  - `appDatabaseExecutor`: returns the on-device executor, `driftDatabase(name: 'na_vrh')` from `drift_flutter`.
  - `appDatabase`: builds `AppDatabase` from the executor and closes it when the provider is disposed (`ref.onDispose(db.close)`).
- Commit the generated `app_database_provider.g.dart` with it.
- Add a test helper in `test/helpers/` that creates a `ProviderContainer` with overrides and disposes it after the test, and one that overrides the executor with an in-memory database.
- Update the README "State management" section with the database provider as the worked example of the conventions (where it lives, keep-alive, how tests override it). If the keep-alive convention line from ticket 1.13 is not in the README yet, add it here.

## Out of scope
- Repositories and any code that reads the database.
- Seeding data.
- Android backup settings and database file location other than the default.
- Closing the database on app lifecycle events beyond the provider's disposal.

## Acceptance criteria
- [ ] The two providers exist, are keep-alive, and are generated and committed.
- [ ] A test, written first, shows that disposing the container closes the database. For example, a query on the database after disposal fails. It uses the in-memory executor override.
- [ ] The test helpers exist in `test/helpers/` and are used by the test above.
- [ ] Manual check on a device, not committed: with a temporary line that reads `appDatabaseProvider` at startup, a debug build creates the database file in the app's documents folder. For example, `adb shell run-as xyz.imkaem.navrh ls` on the app's data directory (on Android the documents folder is `app_flutter`; confirm). The result is noted in the PR.
- [ ] `fvm dart run build_runner build` leaves `git status` clean, and analyze, tests and the format check pass.
- [ ] The README is updated.

## Technical notes
- **Checked ahead of time** in the installed `drift_flutter 0.3.1`: `driftDatabase(name: ...)` takes a required `name`, and by default places the file in the app documents directory (`getApplicationDocumentsDirectory`). The directory can be changed through `DriftNativeOptions`. The exact file name derived from `name` was not checked, so confirm it in the manual device check.
- **Why two providers:** `driftDatabase` needs a platform channel (the documents folder), which a unit test cannot use. Keeping it in its own provider means every test overrides just that one with `NativeDatabase.memory()`, and the real `AppDatabase` wiring (including closing on disposal and the foreign-key step from 1.5) is still exercised.
- **Why keep-alive:** the default `@riverpod` provider is disposed when nothing is listening, which for a database would close and reopen it unexpectedly.
- The app does not read the provider yet, so nothing opens the database until a later ticket's feature does. That is expected.
- The foreign-key pragma comes from `AppDatabase.migration` (1.5), so it applies here without extra setup.

## Decisions
1. **Two providers, executor and database,** so only the platform-dependent part is overridden in tests.
2. **Database name `na_vrh`.**
3. **The database is closed when its provider is disposed.**
