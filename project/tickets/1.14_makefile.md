# 1.14 Makefile for common commands

**Epic:** 1, Project foundations (see [epics.md](../epics.md))
**Spec refs:** section 14 of [SPEC.md](../SPEC.md) (Tooling: "A Makefile wraps the common commands")
**Depends on:** 1.1, 1.3 and 1.5 (done)
**Status:** Todo

## Why
The commands for this project are long and easy to get slightly wrong: they all run from `app/`, and they all go through `fvm`. A Makefile at the repository root gives each one a short name, and gives CI (ticket 1.12) a single command to run, so a developer and CI run exactly the same checks. The root is the right place because the repo is a monorepo and will gain other packages.

## Scope
- Add a `Makefile` at the repository root with these targets (all declared `.PHONY`):

  | Target | Runs |
  |---|---|
  | `help` (the default) | prints every target with a one-line description |
  | `setup` | `fvm install`, then `fvm flutter pub get` in `app/` |
  | `app-run` | `fvm flutter run`, with an optional `DEVICE=<id>` that adds `-d <id>` |
  | `app-test` | `fvm flutter test` |
  | `app-analyze` | `fvm flutter analyze` |
  | `app-format` | `fvm dart format .` |
  | `app-format-check` | `fvm dart format --set-exit-if-changed .` |
  | `app-codegen` | `fvm dart run build_runner build` |
  | `app-codegen-watch` | `fvm dart run build_runner watch` |
  | `app-build-apk` | `fvm flutter build apk --debug` |
  | `app-clean` | `fvm flutter clean` |
  | `check` | `app-format-check`, `app-analyze` and `app-test` together: the checks CI runs |

- Make `help` self-documenting: each target has a `##` comment, and `help` lists them, so the list never drifts from the file.
- Document the targets in the root `README.md` ("Common commands") and mention `make` in `app/README.md`.
- Update `CLAUDE.md`, where the tech stack says the Makefile exists "once it exists", to describe it as present.

## Out of scope
- Release builds and signing (epic 13).
- Targets for other packages, such as the peak data pipeline (epic 2). They get their own prefix when those packages exist.
- Installing `make` or FVM.
- Windows support.

## Acceptance criteria
- [ ] `make` with no arguments prints the target list.
- [ ] Each target above runs successfully on the dev machine (each was run once). `app-run` and `app-build-apk` need a device or a JDK respectively.
- [ ] `make check` passes on `master`, and fails when the code is wrongly formatted, has an analyzer issue, or has a failing test (checked manually, not committed).
- [ ] All targets are `.PHONY`.
- [ ] The root README has a "Common commands" section, and `CLAUDE.md` no longer says "once it exists".

## Technical notes
- Config only, so there is no unit test. The verification is running the targets.
- `make` 4.4.1 is installed on the dev machine, and GitHub's Ubuntu runners should have it too. Check this when writing the CI ticket.
- Each line of a recipe runs in its own shell, so each command is written as `cd app && fvm ...` instead of relying on a separate `cd` line.
- Recipes use a tab for indentation, as `make` requires.
- Keep the commands in the Makefile and the READMEs identical, so the documented commands are the ones that actually run.
- `app-build-apk` needs a JDK. See the JDK item in [todo.md](../todo.md) if Gradle says `JAVA_HOME` is not set.

## Decisions
1. **One Makefile at the repo root,** not one inside `app/`, because the repository is a monorepo.
2. **App targets are prefixed `app-`,** and the shared ones (`help`, `setup`, `check`) are not, so other packages can add their own prefixes later.
3. **`check` is the one command CI runs,** so the local and CI checks cannot drift apart.
4. **Debug builds only** for now. Release builds come with the Play Store epic.
