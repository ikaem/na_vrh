# 1.6 Expedition table

**Epic:** 1, Project foundations (see [epics.md](../epics.md))
**Spec refs:** sections 8 and 10 of [SPEC.md](../SPEC.md) (Expedition management, Data model)
**Depends on:** 1.5 (done)
**Status:** Done

## Why
An expedition is the parent of everything else: routes, and through them readings and photos. It is also the first table with a date column, so this ticket settles how dates are stored for the whole schema. The tickets for the route, reading and photo tables (1.7 to 1.9) follow the patterns set here.

## Scope
- Add `lib/src/data/database/tables/expeditions.dart`: a Drift table `Expeditions`, with the generated row class named `ExpeditionRow` (`@DataClassName('ExpeditionRow')`).

  | Column | Type | Notes |
  |---|---|---|
  | `id` | text, primary key | client-generated UUID, supplied by the caller |
  | `name` | text | required |
  | `coverPhotoId` | text, nullable | a plain column, not a foreign key (see technical notes) |
  | `notes` | text, nullable | |
  | `createdAt` | date and time | stored as UTC |

- Register the table in `AppDatabase` (`tables: [Expeditions]`) and regenerate. The generated `app_database.g.dart` is committed.
- Add `app/build.yaml` with Drift's `store_date_time_values_as_text: true`, so every date column in the schema is stored as ISO-8601 UTC text.
- Add a "Dates" note to the README's code generation or conventions section: dates are stored as UTC text, and read back as UTC.

## Out of scope
- Routes, readings and photos (1.7 to 1.9).
- Generating UUIDs. The caller supplies the ID. A repository ticket creates IDs later.
- Repositories, queries and any domain model. This ticket is the table only.
- `updated_at` and deleted flags for future sync (see `project/todo.md`).

## Technical notes
- **Checked ahead of time** on a throwaway copy of the project:
  - With Drift's defaults, a `DateTime.utc(2026, 1, 2, 3, 4, 5, 678, 9)` was stored as the integer `1767323045` (whole seconds) and came back as a local time (`isUtc` false), without the milliseconds. That breaks the spec's "always UTC" rule.
  - With `store_date_time_values_as_text: true`, the same value was stored as `2026-01-02T03:04:05.678009Z` and came back as UTC, the same instant, with microseconds intact.
- **Ordering:** dates are compared as text in SQL. UTC ISO strings sort correctly, except that a value with a 3-digit fraction (`.678Z`) sorts after one with a 6-digit fraction that shares those digits (`.678009Z`), because `Z` sorts after `0`. This only matters for two times within the same millisecond, so it is negligible here.
- **Why `coverPhotoId` is not a foreign key:** expeditions and photos point at each other (`photos.expedition_id` and `expeditions.cover_photo_id`). A foreign key in both directions makes inserts and deletes awkward, so the cover is a plain column, and the app keeps it consistent (the photos epic handles clearing it when the cover photo is deleted).
- **Row class names:** every table in this schema uses a `...Row` suffix (`ExpeditionRow`, and so on). It keeps the data rows distinct from the domain models that will live in `domain/`, and avoids a real clash that 1.7 hits (see there).
- The schema version stays 1. The app has never been released, so the schema can change freely until ticket 1.10 records the baseline.
- Tests use the existing `createInMemoryDatabase()` helper from `test/helpers/`.

## Decisions
1. **Dates are stored as UTC ISO-8601 text** (the build option above), not as the default integer seconds. It matches the spec's UTC rule, and it keeps full precision.
2. **Row classes use a `Row` suffix** across the schema.
3. **Tables live in `lib/src/data/database/tables/`,** one file per table, in the shared database folder (decision from ticket 1.2).
