# 1.2 Folder structure and conventions

**Epic:** 1, Project foundations (see [epics.md](../epics.md))
**Spec refs:** section 14 of [SPEC.md](../SPEC.md) (testing: pure logic unit-tested without a device)
**Depends on:** 1.1

## Why
Decide where code lives before there is much of it, so later tickets don't each invent their own layout. The structure should also make the spec's testing rule easy: pure logic (haversine, averaging, route state transitions, duration, search) sits apart from UI and is testable without a device.

## Scope
- Set up the base layout under `lib/` (paths relative to the app folder from ticket 1.1):
  - `main.dart`: app entry only (runs the app inside the provider scope later).
  - `app.dart`: the root app widget (theme, home).
  - `core/`: shared helpers with no feature knowledge (time and UTC helpers, constants, theme).
  - `data/database/`: the Drift database and tables. Shared, because the tables reference each other.
  - `features/<feature>/`: one folder per feature, each with `data/`, `domain/`, `presentation/` as needed.
- Move the blank home screen from 1.1 into `features/home/presentation/home_screen.dart`, so the structure has one real example.
- Mirror the layout in `test/` (a test for `lib/features/home/presentation/home_screen.dart` lives at `test/features/home/presentation/home_screen_test.dart`).
- Write the conventions in the README.

Feature folders (`peaks`, `expeditions`, `detection`, `history`, `photos`, `settings`, `export`) are not created now. Each feature's first ticket creates its own folder, so there are no empty placeholder folders.

## Conventions to document
- **Layers inside a feature:**
  - `data/`: repositories and database access.
  - `domain/`: plain Dart models and pure logic (no Flutter, no Drift imports), so it can be unit-tested directly.
  - `presentation/`: screens, widgets, and Riverpod providers.
- **Imports:** package imports (`package:na_vrh/...`), not relative paths, across folders.
- **Boundaries:** a feature may use `core/` and `data/database/`. It does not import another feature's `presentation/`. Shared logic between features moves down into `core/`.
- **Files:** snake_case names, one main public class per file, tests mirror source paths.

## Out of scope
- Navigation or routing choice (separate ticket in epic 1).
- Lint rules (1.3), Riverpod (1.4), Drift (1.5).
- Creating folders for features that don't exist yet.

## Acceptance criteria
- [ ] `lib/` has `main.dart`, `app.dart`, `core/`, `data/database/`, and `features/home/` as described.
- [ ] The home screen lives in `features/home/presentation/`, and its smoke test from 1.1 is moved to the mirrored path in `test/` and passes.
- [ ] `flutter run` and `flutter test` still work.
- [ ] The README has a short "Project structure and conventions" section covering the rules above.

## Open decisions
1. **Three layers per feature (`data/domain/presentation`) or flat feature folders?** Recommendation: the three layers, since `domain/` is where the spec's unit-tested logic lives. The cost is a few extra folders for small features.
2. **Drift tables in shared `data/database/`, or split per feature?** Recommendation: shared. Routes, photos and expeditions all reference each other, and one place keeps the schema and migrations (1.10) together.
3. **Package imports everywhere, or relative within a feature?** Recommendation: package imports everywhere, for consistency.
