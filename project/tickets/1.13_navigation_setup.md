# 1.13 Navigation setup

**Epic:** 1, Project foundations (see [epics.md](../epics.md))
**Spec refs:** section 14 of [SPEC.md](../SPEC.md) (Tech stack)
**Depends on:** 1.2 and 1.4 (both done)
**Status:** Todo

Numbered 1.13 to avoid renumbering the tickets already saved. Execution order comes from "Depends on", not from the number.

## Why
Nearly every feature adds screens: the peak picker, expedition detail, detect result, history, settings, photos, export. Deciding how screens connect now means each feature ticket just adds a route, instead of inventing its own navigation.

## Scope
- Add `go_router` and switch the app to `MaterialApp.router`.
- Make `NaVrhApp` (`lib/src/app.dart`) a `ConsumerWidget` that passes `routerConfig: ref.watch(appRouterProvider)` to `MaterialApp.router`. Keep the title `na_vrh`.
- Create the router as a `@Riverpod(keepAlive: true)` provider in `lib/src/app_router.dart`, so it can be overridden in tests. The default `@riverpod` provider is disposed when nothing is listening, which is wrong for a router. Its generated `.g.dart` file is committed with it (conventions from ticket 1.4).
- In `app_router.dart`, expose the route list (for example as `appRoutes`) separately from the provider, so tests can build a router from the same routes instead of copying them. It contains one real route: home (`/`).
- Add `lib/src/core/routing/route_paths.dart` with plain string constants and path-builder helpers (for example a path with an expedition ID parameter). No screen imports. The builders are real logic, so they get tests first, in `test/src/core/routing/route_paths_test.dart`.
- Add a "page not found" screen in the app layer (`lib/src/not_found_screen.dart`), used as the router's error page. It is static, so it has no test of its own. The unknown-path widget test below covers it.
- Update `test/src/app_test.dart`: `NaVrhApp` now needs a `ProviderScope`, so the existing tests, which pump it without one, fail until they are updated.
- Add a test helper in `test/helpers/` that pumps the app with a router starting at a given path (built from `appRoutes`, installed by overriding `appRouterProvider`).
- In `app/README.md`:
  - add a short note on how to add a route (path constant, route entry in `appRoutes`),
  - add a provider lifetime convention to the "State management" section: providers that own a long-lived resource (the router, later the database) use `@Riverpod(keepAlive: true)`,
  - fix the line "Folders are created by the first ticket that needs them, so `core/`, `data/database/` and `features/` do not exist yet". `data/database/` has existed since ticket 1.5, and `core/` will exist after this ticket.

## Why the router lives outside `core/`
The router must import screens from every feature. Under the 1.2 boundary rule, `core/` can't know about features, so `app_router.dart` sits in the app layer at the top of `lib/src/`, next to `app.dart`. Features navigate through the plain path strings in `core/routing/`, which avoids circular imports between features and the router.

## Out of scope
- Bottom navigation bar or other app-wide layout. That is a UI decision for when there are real screens to arrange.
- Deep links and custom page transitions.
- Routes for screens that don't exist yet. Each feature adds its own route in its first ticket.

## Technical notes
- Checked ahead of time on a throwaway copy:
  - `go_router` resolves with the current dependencies (version `^18.1.4` at the time).
  - `@Riverpod(keepAlive: true)` generates `isAutoDispose: false`.
  - A test that overrides the router with `appRouterProvider.overrideWithValue(GoRouter(initialLocation: '/nope', ...))` shows the error page, and `fvm flutter analyze` is clean with the strict lint rules.
  - The existing `app_test.dart` fails once `NaVrhApp` needs a `ProviderScope`, as described above.
- Path parameters carry IDs (UUIDs), for example `/expedition/:id`. Pass IDs, not whole objects, so a screen loads its data from the database and survives a process restart.
- If a bottom navigation bar is chosen later, `go_router`'s `StatefulShellRoute` supports it without changing this setup.

## Decisions
1. **`go_router`, not plain `Navigator`.** It is maintained by the Flutter team, handles ID parameters cleanly, and works well with Riverpod. Plain `Navigator.push` would also work for a small app, but gets messier with parameters and testing.
2. **The router is a Riverpod provider, not a plain global,** for testability.
3. **The router provider is keep-alive,** because a router must live as long as the app.
