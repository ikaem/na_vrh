## Why
Riverpod is the chosen state management, with code generation. Wire it once at the root, set up the code generation tooling (which Drift in 1.5 reuses), and write down where providers live, so later tickets (1.11 database provider, 1.13 router provider, and every feature) follow one pattern.

## Scope
- Add `flutter_riverpod` and `riverpod_annotation` to the dependencies, and `riverpod_generator` and `build_runner` to the dev dependencies (current versions).
- Wrap the app in `ProviderScope` in `lib/main.dart`.
- Set up code generation for the whole app (ticket 1.5 reuses this):
  - Ignore `*.g.dart` in `app/.gitignore`, so generated files are not committed.
  - Exclude `**/*.g.dart` from analysis in `analysis_options.yaml`, as a precaution.
  - Document codegen in `app/README.md`: the command, and that a fresh clone must run it before `analyze`, `test` or `run`.
- Add a "State management" section to `app/README.md`: how to write providers, where they live, and how tests override them.
- Correct both places in `app/README.md` from ticket 1.2 that say Riverpod providers live in `presentation/` (the layout tree comment and the layers list), to match the conventions below.
- In `CLAUDE.md`, extend the rule that `domain/` has "no Flutter or Drift imports" to also say no Riverpod, and note that generated files are not committed and how to generate them.
- Do not add an example provider. It would be dead code. The first real provider arrives with the database provider in 1.11.

## Conventions to document
- **Writing providers:** with the `@riverpod` annotation. Use a function for a simple or read-only provider, and a class (a notifier) when there is state with methods. Parameters are plain function arguments. Each file with annotated providers has a `part 'name.g.dart';` line. Do not use the legacy provider types (the package keeps them behind a separate `legacy.dart` import).
- **Codegen:** run `fvm dart run build_runner build` after changing annotated code, or `fvm dart run build_runner watch` while developing. Generated files are not committed.
- **Where providers live:**
  - Repository and service providers go in the feature's `data/` (the database provider goes in `data/database/`).
  - UI state providers go in `presentation/`.
  - `domain/` never imports Riverpod. It stays plain Dart.
- **Tests:** override with `ProviderScope(overrides: [...])` in widget tests and `ProviderContainer(overrides: [...])` in unit tests.

## Technical notes
- Checked ahead of time on a throwaway copy:
  - These packages resolve together: `flutter_riverpod ^3.5.0`, `riverpod_annotation ^4.0.8`, `riverpod_generator ^4.0.10`, `build_runner ^2.17.1`. They also resolved together with `drift`, `drift_flutter` and `drift_dev` (ticket 1.5).
  - A `@riverpod` function with a parameter generated a family provider (`xyzProvider(arg)`), and `fvm dart run build_runner build` produced the `.g.dart` file. The first build took about 30 seconds.
  - `fvm flutter analyze` passed with the strict modes and the 1.3 lint rules, with and without the `**/*.g.dart` exclude. So the exclude is a precaution here, and may be needed for Drift's output in 1.5. A `part` directive does not trip `always_use_package_imports`.
- In Riverpod 3, annotated provider functions take a plain `Ref ref`, with no per-provider ref types.
- Generated files are not committed, which fits the one-production-file-per-commit rule.
- No test is added beyond the existing smoke tests: this ticket is wiring and tooling, per the project's testing rules.

## Decisions
1. **Code generation (`riverpod_generator`) is adopted.** This changes the earlier decision for plain providers. Reasons: the app will have many providers that take a parameter (expedition by ID, routes of an expedition, peak search by query), which are much simpler as annotated functions than as `.family` providers, and `build_runner` is already needed for Drift. Trade-off: every change to a provider needs a codegen run (use `watch` while developing), and there are more generated files.
2. **Repository providers live in `data/`.** This refines ticket 1.2, which put all providers in `presentation/`, so that `presentation/` does not own data wiring.
3. **The codegen setup lives in this ticket,** and ticket 1.5 reuses it, because 1.4 comes first.
