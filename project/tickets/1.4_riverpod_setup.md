# 1.4 Riverpod setup

**Epic:** 1, Project foundations (see [epics.md](../epics.md))
**Spec refs:** section 14 of [SPEC.md](../SPEC.md) (Tech stack: Riverpod)
**Depends on:** 1.2 (done)
**Status:** Todo

## Why
Riverpod is the chosen state management. Wire it once at the root and write down where providers live, so later tickets (1.11 database provider, 1.13 router provider, and every feature) follow one pattern.

## Scope
- Add `flutter_riverpod` (current major version) to the dependencies.
- Wrap the app in `ProviderScope` in `lib/main.dart`.
- Add a "State management" section to `app/README.md`: where providers live, which provider types to use, and how tests override them.
- Update the README line from ticket 1.2 that says Riverpod providers live in `presentation/`, to match the conventions below.
- Do not add an example provider. It would be dead code. The first real provider arrives with the database provider in 1.11.

## Out of scope
- `riverpod_generator` and Riverpod lint tooling (see decision 1).
- A shared test helper for overriding providers. It is written with the first real provider (1.11), and 1.13 has its own router helper.
- The providers themselves.

## Acceptance criteria
- [ ] `flutter_riverpod` is in `pubspec.yaml` and `main.dart` runs `NaVrhApp` inside a `ProviderScope`.
- [ ] The existing tests pass, `fvm flutter analyze` is clean, and the app still runs.
- [ ] The README documents the provider conventions below, and the old line about providers in `presentation/` is corrected.

## Conventions to document
- **Provider types:** `Notifier` / `AsyncNotifier` and plain `Provider` for the current Riverpod version, not the legacy provider types. Check the current API when implementing.
- **Where providers live:**
  - Repository and service providers go in the feature's `data/` (the database provider goes in `data/database/`).
  - UI state providers go in `presentation/`.
  - `domain/` never imports Riverpod. It stays plain Dart.
- **Tests:** override with `ProviderScope(overrides: [...])` in widget tests and `ProviderContainer(overrides: [...])` in unit tests.

## Technical notes
- This is a thin ticket: wiring only, so no test beyond the existing smoke tests, per the project's testing rules. It stays separate because 1.13 depends on it.

## Decisions
1. **Plain providers, no code generation (`riverpod_generator`).** Drift already brings `build_runner` (1.5), and a second code generator for providers adds moving parts without much gain at this size. It can be adopted later.
2. **Repository providers live in `data/`.** This refines ticket 1.2, which put all providers in `presentation/`, so that `presentation/` does not own data wiring.
