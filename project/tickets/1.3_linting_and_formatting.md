# 1.3 Linting and formatting

**Epic:** 1, Project foundations (see [epics.md](../epics.md))
**Spec refs:** section 14 of [SPEC.md](../SPEC.md) (Testing)
**Depends on:** 1.1 (done)
**Status:** Todo

## Why
Set the rules before more code exists. Stricter lints added later mean changing files that were already reviewed. The rules should also back up the conventions we have written down, such as package imports everywhere.

## Current state
`flutter_lints` is included and nothing else is configured. `analysis_options.yaml` excludes `build/`, `android/` and `ios/`, and has an empty `linter: rules:` list.

## Scope
- Keep `flutter_lints` as the base.
- Turn on the strict analyzer modes (`strict-casts`, `strict-inference`, `strict-raw-types`) under `analyzer: language:`.
- Enable these extra rules: `always_use_package_imports`, `prefer_single_quotes`, `directives_ordering`, `unawaited_futures`, `prefer_final_locals`, `sort_pub_dependencies`.
- Fix the violations in the existing code. Checked against these rules ahead of time: the Dart code in `lib/` and `test/` has none, and the only findings are 2 `sort_pub_dependencies` infos in `pubspec.yaml` (dependencies and dev dependencies need alphabetical order). CI runs with `--fatal-infos`, so these must be fixed here.
- Explain the choices in short comments inside `analysis_options.yaml`.
- Keep `dart format` at its defaults.

## Out of scope
- Running these checks in CI (1.12).
- Excluding generated Drift files from analysis (1.5).
- Riverpod-specific lints (1.4).
- Enforcing import boundaries (see technical notes).

## Acceptance criteria
- [ ] `analysis_options.yaml` has the three strict modes and the extra rules listed above.
- [ ] `fvm flutter analyze` reports no issues.
- [ ] `fvm dart format --set-exit-if-changed .` passes.
- [ ] Spot check: temporarily adding a relative import and a double-quoted string is reported by the analyzer (not committed).

## Technical notes
- Config only, so there is no unit test. The spot check above is the verification.
- `always_use_package_imports` enforces the "package imports across folders" convention from ticket 1.2 automatically.
- Standard lints cannot enforce "a feature never imports another feature's `presentation/`" or "`core/` never imports features". Options for later: a small test that scans import lines (no dependency), or an import-lint package. Not part of this ticket.

## Decisions
1. **Ruleset:** `flutter_lints` plus the short list of extras above. A stricter opinionated package such as `very_good_analysis` enables many rules at once, which is more to review for little gain at this size.
2. **Extra rule list:** as listed in the scope.
3. **Infos in CI:** CI (1.12) runs `analyze --fatal-infos`, so infos fail the build there while still showing as hints locally.
