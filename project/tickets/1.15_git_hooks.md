# 1.15 Git hooks: run tests before push

**Epic:** 1, Project foundations (see [epics.md](../epics.md))
**Spec refs:** section 14 of [SPEC.md](../SPEC.md) (Tooling)
**Depends on:** 1.14 (the Makefile and its `app-test` and `setup` targets)
**Status:** Todo

## Why
A push with failing tests should be stopped on the developer's machine, not found later in review. The tests run in seconds, so this is cheap. A hook can be skipped, so it does not replace CI (ticket 1.12, still a placeholder). It is a local safety net in the meantime.

## Scope
- Add `.githooks/pre-push`, a POSIX `sh` script, committed with the executable bit:
  - If every ref being pushed is a deletion, do nothing and succeed.
  - Otherwise run `make app-test` from the repository root. If it fails, print a short message saying the push was blocked and that `git push --no-verify` skips the hook, and exit with a failure so the push stops.
  - If `make` or `fvm` is not available, print a clear message and fail, instead of silently skipping the tests.
- Add a `hooks` target to the Makefile that runs `git config core.hooksPath .githooks`, and make `make setup` run it.
- Add a "Git hooks" section to the root `README.md`: what runs on push, how the hooks get installed (`make setup` or `make hooks`), and how to skip them with `git push --no-verify`.

## Out of scope
- Other hooks, such as `pre-commit` or `commit-msg`.
- Running formatting or analysis on push (see decision 2).
- CI (1.12).
- A hook manager tool.

## Acceptance criteria
- [ ] `.githooks/pre-push` is committed and executable.
- [ ] After `make hooks`, `git config core.hooksPath` prints `.githooks`, and `make setup` does the same.
- [ ] Manual check, not committed, against a temporary local bare repository as the remote: a push is blocked when a test fails, and the remote does not receive the commit.
- [ ] The same check: a push with passing tests goes through, and `git push --no-verify` goes through even with a failing test.
- [ ] The same check: deleting a remote branch does not run the tests.
- [ ] The README section is added.

## Technical notes
- **Checked ahead of time** with a throwaway repository and a bare remote (Git 2.51.0):
  - A `pre-push` hook that exits with a failure stops the push, and the remote does not receive the commit.
  - `git push --no-verify` skips the hook.
  - The hook receives the remote name and URL as arguments, and one line per pushed ref on standard input: `<local ref> <local hash> <remote ref> <remote hash>`. For a deletion, the local ref is `(delete)` and the local hash is all zeros. That is how the script recognizes a deletion-only push.
- **Why `.githooks/` and `core.hooksPath`:** the real hooks folder, `.git/hooks/`, is not part of the repository, so nothing there can be shared. A committed folder plus one line of local config shares the script. That config is per clone, which is why a fresh clone has no hooks until `make setup` (or `make hooks`) runs.
- **Limitation:** the tests run against the working tree, not against the commits being pushed. Uncommitted changes can make a pass or a failure not reflect what is actually pushed. That is normal for a simple pre-push hook.
- The first test run needs network access, because Drift's SQLite binary is downloaded then (finding in ticket 1.5). A first push on a fresh machine without network fails for that reason.
- Claude never runs `git push` (see `CLAUDE.md`), so the hook only affects pushes you make.

## Decisions
1. **A plain shell script with `core.hooksPath`,** not a hook manager. No extra dependency to install.
2. **Tests only,** as requested, via `make app-test`. Formatting and analysis are not run on push. `make check` could replace it later if you want those too.
3. **Fail with a message when `make` or `fvm` is missing,** so a missing tool never hides the tests.
4. **Hooks are installed through `make setup`,** so setting up a clone is one command.
5. **Deletion-only pushes skip the tests.**
