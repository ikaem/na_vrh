# 1.9 Photo table

**Epic:** 1, Project foundations (see [epics.md](../epics.md))
**Spec refs:** sections 8, 9 and 10 of [SPEC.md](../SPEC.md) (Expedition management, Photos, Data model)
**Depends on:** 1.7
**Status:** Todo

## Why
Photos attach to an expedition, and optionally to one of its routes. This table is also where the spec's delete rule for routes lives: deleting a route keeps its photos, and moves them up to the expedition.

## Scope
- Add `lib/src/data/database/tables/photos.dart`: a Drift table `Photos`, with the row class named `PhotoRow` (`@DataClassName('PhotoRow')`).

  | Column | Type | Notes |
  |---|---|---|
  | `id` | text, primary key | UUID |
  | `expeditionId` | text | foreign key to `expeditions.id`, `ON DELETE CASCADE` |
  | `routeId` | text, nullable | foreign key to `routes.id`, `ON DELETE SET NULL`. Null means an expedition-level photo |
  | `filePath` | text | path of the copied image file (see decision 1) |
  | `takenAt` | date and time, nullable | UTC |
  | `caption` | text, nullable | unused in v1 |

- Add indexes on `expeditionId` and `routeId`.
- Register the table in `AppDatabase` and regenerate (the generated file is committed).

## Out of scope
- Picking, resizing, copying and deleting image files (the photos epic).
- Cover photo logic. `expeditions.coverPhotoId` and `routes.coverPhotoId` are plain columns from 1.6 and 1.7.
- Moving a route between expeditions.

## Acceptance criteria
- [ ] `Photos` exists with the columns above, registered in `AppDatabase`.
- [ ] A test round-trips an expedition-level photo (`routeId` null) and a route-level photo. Written first.
- [ ] Deleting a route keeps its photos and sets their `routeId` to null (SPEC.md section 8). Written first.
- [ ] Deleting an expedition deletes its photos, both the expedition-level ones and the ones attached to its routes. Inserting a photo for a missing expedition is rejected. Written first.
- [ ] `build_runner` leaves `git status` clean, and analyze, tests and the format check pass.

## Suggested units
1. The table file.
2. Registration in `AppDatabase`, the indexes, the regenerated file, and the tests. The tests use the fixture helpers from 1.7.

## Technical notes
- The two foreign keys use different delete actions on purpose: deleting an expedition cascades (photos go), deleting a route only clears `routeId` (photos stay). The cascade and set-null behavior were both checked working on a throwaway copy, with the foreign-key pragma from 1.5.
- **Rules the database does not enforce, left for the epics that use this table:**
  - A photo's route must belong to the photo's expedition.
  - When a route moves to another expedition (SPEC.md section 8), its photos' `expeditionId` must move with it (epic 4).
  - When a photo is deleted or moved, any cover reference to it (`coverPhotoId` on an expedition or route) must be cleared, because those columns have no foreign key (see 1.6).
- After this ticket all four tables exist. Ticket 1.10 then records the schema as the version 1 baseline.

## Decisions
1. **`filePath` holds a path relative to the app's photo folder,** not an absolute path. The app's storage location can change (a restore, a new install), and a relative path survives that. The photos epic resolves it to a full path.
2. **`PhotoRow` for the row class,** following the `Row` suffix convention from 1.6.
3. **Indexes on both foreign keys.**
